## 2. Social coinflip: player vs player **OR** player vs house bot

Use subcommands not duplicate conflicting routes. Never execute game immediately on preview.
**Match lifecycle:** DRAFT -> OPEN (stake escrowed) -> ACCEPTED (both stakes escrowed) -> ANIMATING -> SETTLED; branches EXPIRED / CANCELLED / VOIDED (with atomic full refunds). UI shows challenger avatar/name, stake, chosen side, fairness commitment, odds, pot, house fee, winning total, waiting timer and buttons `🤝 Join`, `👤 Challenge Friend`, `🤖 Play House`, `❌ Cancel`, `🛡️ Fairness`. Joiner automatically takes opposite side or explicitly accepts; disallow self-join, same linked identity, blocked user, bad balance, paused players, invalid guild. Invite-specific matches check invitee identity. Every state transition uses locked database transaction and unique idempotency keys; cross-server matches disabled initially. On timeout after player 1 escrow, refund once, mark expired, cancel button and notify once. On accepted match both sides fixed; no cancellation without void rules. Handle bot restart mid-animation: result calculated/stored server-side, presentation resumes from persisted match.
**PVP pot rake with 5% mathematical edge:** both stake `s` SC, combined pot `2s`; fee 5% of POT = `0.10s`; winning player receives `1.90s`; losing player 0. Example 100 SC + 100 SC => 200 SC pot, 10 SC fee, winner receives 190 SC total (= 90 SC net gain), loser loses 100 SC. With equal 50/50 probabilities each player's EV = 0.5*(+90)+0.5*(-100) = -5 SC per 100 SC stake = 5% stake edge. At total-pot level operator retains 10 SC per match. Disclose both fee relative to pot (5%) and effective expected loss relative to each player's stake (5%).
**Integer SC rule:** require stakes multiple of 10 SC for 5% exact pot fee (fee = stake/10) or implement a publicly documented round-down distribution/fee rule. Do not advertise exact 5% if rounding changes it. A player-vs-house bot always risks one user stake and returns 1.90x stake on winning a 50/50 draw; house bankroll is virtual and matches are not represented as coming from another player's wallet. Simulate visually as 'ByteBits House Dealer 🤖' with portrait and moving coin.
**Optional 4% variant:** PvP fee = 4% total pot, win returns `1.92s`; house-bot wins return 1.92x. Provide exactly one advertised mode fee per match and freeze it at creation. DO NOT add both 5% pot fee and a 1.9x payout adjustment (double-fee); the 1.90x *is the result* of the 5% pot fee.
**Animation:** Discord embed/image/GIF is not a real-time controllable animation; send a 'Flipping...' message then edit to the final settled card, or use animated GIF/APNG attachment. For true smooth spinning 3D coin, particles, sound, mobile responsive UI and avatars use the Discord Activity (React + Canvas/PixiJS). Animation reveals stored result and never computes result client-side. Offer reduced motion and no sound defaults. Avoid manipulative near-misses.
**Match storage:** coinflip_matches(id,guild_id,creator_id,opponent_id,mode,visibility,side,stake_sc,fee_sc,pot_sc,winning_return_sc,state,seed_commitment,server_seed_encrypted_or_protected,client_seed_a,client_seed_b,nonce,paytable_version,expires_at,accepted_at,settled_at,winner_id,proof_id,interaction_message_id,created_at); match_events, escrow journal lines; unique `(guild_id,id)` and `(match_id,joiner_id)` constraints, DB check `stake_sc>0`. **Tests:** simultaneous joins => only 1 match accepted; concurrent match & single-player bets never overspend; stale UI click rejected; funds escrowed/refunded once on expiry; a valid join after expiry rejected; duplicate webhooks idempotent; seed commit before join; reveal after sides locked; expected win count ~50% in a large reproducible simulation; fee/winner payment exact for 100 SC; server restart during animation settles once; blocked/unavailable player handling.
